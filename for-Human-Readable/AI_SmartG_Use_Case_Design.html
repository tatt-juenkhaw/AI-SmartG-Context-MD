Enhanced AI Training Workflow

Use Case & UI Reference

This document consolidates the use case design, interaction flows, and UI illustrations built for the Enhanced AI Training Workflow — automatically assigning inspection criteria to every part on a board from RGB images and 3D heatmap alone, with minimal user input, and a guided path for the user to review and fine-tune the result.

Everything below was reviewed in a design session on 8/9. Points raised in that session are called out inline as Review Feedback boxes, matching the "9/9 Update" annotations from the reviewed deck. Anything still unresolved as of this writing is called out separately as an Open Item, and collected at the end.

The two phases — Auto Train (generates a parameter database from scratch) and Device Review (lets the user validate and fine-tune it) — are each broken into their constituent steps, with the interactive mockup for that step embedded directly below its explanation.

Foundations

Design Consideration

  • Seamless integration of modules in the programming experience — a smooth pipeline between segregated modules (AI Param Profile, Auto Train, Recipe QC, Negative Test, Advanced Parameter…).
  • Insightful clues to lead the user through completing review and fine-tuning the AI Setup device.
  • Data-driven presentation to boost user confidence in AI Setup accuracy.
  • Keep each module purpose-guided in the presentation layer; keep the pipeline generic in the backend layer.
  • Tailor-made algorithms (Coplan, etc.) remain available on the Editor — an extra parsing layer makes them compatible with the generic algorithm (3D Box) pipeline underneath, so nothing validated has to be thrown away.
Foundations

New Device Concept

1. Single Generic Algorithm Container (U-Type) retires the customized pipeline per CBRS category, encouraging a modular, generic algorithm design that reduces maintenance. Existing algorithm customization stays in the UI layer, but inspection runs through the same generic pipeline in the backend.

CBRS (today)U-Type (proposed)
User-facing screen"Coplanarity Setup""Coplanarity Setup" — unchanged
Backend algorithmCustom Coplan pipeline, built specifically for this categoryGeneric 3D Box-to-Box comparison
What the user relearns—Nothing
What engineering maintainsA separate pipeline per category, per criterionOne pipeline, reused across every package

2. "Package" as the primary tier of device/part classification, instead of device type — improves syncing of algorithm coverage, threshold standard, and data analysis across the same package, and scales better than recognizing the first letter of a device type (the CBRS approach).

Foundations

Threshold Parameter Concept

Prioritize percent over micron — a shared unit across modules, algorithms, and standard definitions eases syncing; it's quantifiable in data analysis for reference values; and it's resilient to geometry/height changes, saving fine-tuning time. Micron stays tunable — every threshold parameter pairs with both percent and micron, synced to each other.

Micron threshold (fixed)Percentage threshold
RuleLift > 50 µm = defect (tuned for Part A)Lift > 10% of lead height = defect
Part A — 0.5mm lead height50 µm — correctly tuned10% × 500µm = 50µm — same result
Part B — 1.2mm lead heightStill 50µm — now only ~4% deviation10% × 1200µm = 120µm — equivalent severity
Re-tuning needed for Part B?Yes — someone must notice and manually derive a new valueNo — the same rule applies directly
Review Feedback — 9/9
Parameters requiring reference from part size/height are the only ones where percentage prioritization over micron applies. Locator Offset and Lifted Lead qualify — Coplanarity does not.
Resolved
The three illustrations that originally used Coplanarity as the percent-primary worked example — the AI Setup median example, the Fine-Tune UI, and the Drift & Apply screen — have been updated to use Locator Offset instead, referenced against body size (not body height, which was Coplan's reference dimension and no longer applies). Coplanarity itself remains in the coverage matrix as a real criterion; it's just no longer the drill-down example for the percent-primary pattern.

End-to-End Use Case Overview

A new program starts with an empty database. The user triggers AI Setup; Auto Train and Device Review then run as two connected phases, exchanging artifacts, until the program is production-ready.

Auto Train

  1. User triggers AI Setup
  2. User defines algorithm coverage and preset parameters by package
  3. AI locates Body / Lead / Joint and Height
  4. AI Param Config presets threshold parameters
  5. Performs Negative Test with AI Synthetic Defect Images (deprioritized — see review note below)
  6. Performs Abnormalities Analysis on AI inference data
  7. Flags Auto Train status for user review

Device Review

  1. User reviews AI Setup
  2. User identifies package type / locates unrecognized parts manually, as a template for AI
  3. User triggers AI Param Config to preset threshold parameters
  4. User fine-tunes flagged threshold parameters with reference values from analysis
  5. User proliferates the fine-tuned standard to package level for reuse
AI Setup Artifacts (Auto Train → Device Review)User-defined inspection criteria and standard by package · AI segmentation and inference data by part/package · Trained database with AI flags.
Device Review Artifacts (loops back / forward)User fine-tuned inspection standard by package · AI template for unrecognized parts · Fine-tuned database — feeds back into Auto Train for reuse, and forward into a production-ready program.
Review Feedback — 9/9
Negative Test with Synthetic Images is not being pursued right now — parallelism between it and Auto Train isn't achievable at the moment, and it's a programming-time concern. Treat it as optional/future scope wherever it appears below, not near-term.
AUTO TRAIN
Auto Train · Step 1

Algo Coverage + AI Param Config

A one-stop UI for both algorithm coverage checking and threshold presets by package. Before Auto Train runs, the user performs a quick confirmation on coverage and, if necessary, checks the preset parameters. Multiple preset profiles are possible.

Screen 1: on/off coverage matrix by package type × criteria. Screen 2: Locator Offset preset detail for SOIC — X/Y offset tolerance as % of body size, Skew tolerance in degrees, and an IPC Class/Custom selector.
Auto Train · Step 2

AI Setup & Median Aggregation

For each part, AI segmentation runs on every sample (refdes); the final ROI and every downstream measurement is set from the median across all samples, not any single instance. Raw inference data is retained for the abnormality analysis step. Thresholds are set up from median body/lead size and height, combined with the preset from AI Param Config.

Review Feedback — 9/9
All AI inference, including the Classifier itself, adopts the median value — not just geometric measurements. Speed is a primary concern here, since this now means running AI models on every component, not a sample.
Card 1: AI locating Body/Lead/Solder across three SOIC samples, with range bars showing raw spread and median. Card 2: preset % combined with the measured median to produce an effective threshold — Locator Offset/Lifted Lead scale the preset, Solder Coverage validates it instead.
Auto Train · Step 3

Setup Abnormalities Analysis

Detects abnormally high variance in AI inference results within the same part, and is able to filter outlier data from genuinely defective units. This gives data-driven clues for the user — which device, and which part of that device, needs attention or manual input.

Review Feedback — 9/9
Aside from AI/3D abnormal performance (high variance), it's also possible to detect a CAD offset when a part shows a high median on locator offset — a systematic shift, not sample-to-sample noise.
Open Item
The illustration below covers high-variance flags (Count of Lead, Lead Height, Body Size, Solder Size, Body Height) routed to three review-action categories. High median on Locator Offset as a CAD-offset signal is a distinct pattern — a systematic deviation rather than a spread — and isn't yet represented as a fourth category. Worth adding a "systematic offset" row alongside the existing variance rows in a future revision.
Card 1: five parameters flagged for high variance, color-coded by category. Card 2: each category routed to the specific action the user needs to take.
Auto Train · Step 4

Classify Auto Train Outcome + Outcome Report

Three outcomes from the four-stage pipeline (AI Classify → AI Locate ROI → Param Preset → Abnormality Analysis): a clean pass is Complete; a pass that gets flagged at Abnormality Analysis is Complete with Risk; failing to classify (unknown class) or locate (can't find body/lead) is Failed — Manual Setup Required.

  • Status is backed by data analysis, giving the user confidence in what they're looking at.
  • Setup abnormalities are pinpointed, so the user has a concrete clue — an action item — rather than a bare flag.
  • The report doubles as a checklist toward a production-ready database.
Card 1: pipeline stage diagram showing which failure routes to which outcome. Card 2: a sample by-part results table with detected package type and pinpointed issue per flagged row.
DEVICE REVIEW
Device Review · Step 1

Starting with Unrecognized Parts

The user is guided to the serious setup failures first — proceeding directly to the Editor page, with the Auto Train checklist as the primary guideline to follow. The interaction:

  • Guide the user to start with the serious setup failure first.
  • User manually identifies package type / locates the missing ROI — minimal effort (one rough box, one dropdown).
  • Trigger Auto Setup again for that part, run abnormality analysis, and update the outcome status.
  • Few-shot learning lets the AI model learn from the user-defined template on unrecognized parts.
Review Feedback — 9/9
Few-shot learning is applicable across the whole program, not just to future occurrences within one session — and it applies to the Classifier as well, not only ROI location. Centralizing user-defined templates (potentially across programs) is a future consideration.
Four-panel flow across User / UI / AI Module: triage the failed part first, minimal manual input, rerun through the same pipeline as any other part, then save the template for few-shot learning on the next occurrence.
Device Review · Step 2

Fine Tuning Threshold

The user stays in charge of deciding the final parameter value, but with adequate data support for that decision. Each threshold parameter is equipped with reference values from two sources: Visit All results (range, median) and values across parts of the same package (range, median), with a clear indicator on the preset (golden standard) value.

Review Feedback — 9/9
The two reference sources are prioritized, not just presented side by side: Visit All is preferred when there's an abundant sample of the same part — i.e. programming on a good board. Package Standard is the reference for a recipe that's freshly generated and hasn't yet been through Visit All or fine-tuning. Reference accuracy could improve further with access to centralized production result data.
Open Item
The Fine-Tune UI below presents Visit All and Same Package as two parallel, equally-weighted rows. The prioritization logic above — Visit All takes precedence once available, Package Standard is the fallback before that — isn't yet visually encoded (e.g. dimming or reordering whichever source is less authoritative at a given point in the part's lifecycle). Worth a follow-up revision.
Percent-primary slider with a synced micron textbox; two aligned reference rulers (Visit All, Same Package) sharing one scale so the current setting, the median, and the golden standard all line up visually.

Note: this screen uses Locator Offset as the worked example, referenced against body size — the criterion the 9/9 review confirmed actually justifies percent-primary treatment.

Device Review · Step 3

Adapt as New Package Standard

With abundant data from fine-tuning, the UI can flag that the current golden standard is shifting away from the median of the actual parameter values in use. The user can then decide whether to adopt the current median as the new golden standard for every part of the same package — a closed-loop ecosystem where the user's own fine-tuning work improves Auto Param Setup accuracy over time.

Card 1: five SOIC parts fine-tuned in sequence, trending away from the 8% golden standard. Card 2: the fine-tune UI extended with two independent controls — apply to all existing parts in the package, and/or set as the new golden standard for future parts.
Wrap-up

Open Items / Follow-ups

Consolidated from the flags raised throughout this document:

  • Coplanarity percent-vs-micron conflict — resolved. Locator Offset and Lifted Lead justify percent-over-micron (both scale with part size/height); Coplanarity does not. The three illustrations that used Coplan as the worked example (AI Setup median example, Fine-Tune UI, Drift & Apply) now use Locator Offset against body size instead.
  • CAD-offset detection. A high median (not just high variance) on Locator Offset can indicate a systematic CAD offset — a fourth abnormality category distinct from the variance-based ones currently illustrated.
  • Negative Test with Synthetic Images is deprioritized for now (parallelism with Auto Train isn't feasible yet) — treat as optional/future wherever it appears in the flow.
  • Few-shot learning scope. Applies program-wide and to the Classifier itself, not just ROI templates for one part going forward. Centralized template storage across programs is a future idea, not yet designed.
  • Fine-Tune reference prioritization. Visit All should take precedence over Package Standard once available; the current UI shows both as equal-weight, unprioritized rows.
  • "Direct to Editor page" navigation for serious setup faults — confirm this matches the real app's actual page/navigation structure; illustrated here as a generic concept, not tied to a specific page name.
